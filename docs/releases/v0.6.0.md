## Summary

S06 adds the platform's human identity, encrypted broker-credential store,
immutable audit trail, short-lived access tokens, rotating refresh sessions,
tenant-scoped role authority, and permissive row-level-security scaffolding. The
security-observability surface is bounded and subjected to deliberate secret-leak
probes.

The release candidate also remediates the reported Starlette advisories. FastAPI
`0.133.1` is the smallest preferred patch after explicit Starlette 1.x support;
its deployment graph resolves Starlette `1.3.1`. The deployed dependency lock is
now the authoritative input to both the vulnerability audit and the release SBOM.

## Dependency-security remediation

| Package | Before | After | Relationship | Reason |
|---|---:|---:|---|---|
| FastAPI | 0.121.1 | 0.133.1 | direct runtime | Smallest preferred candidate with explicit Starlette 1.x support |
| Starlette | 0.49.3 | 1.3.1 | transitive runtime | Fixed line required to remove the five reported advisories |
| httpx | 0.28.1 | removed | direct development | Legacy client emits a fatal deprecation warning with Starlette 1.3.1 |
| httpcore | 1.0.9 | removed | transitive development | Dependency of the removed legacy client |
| httpx2 | absent | 2.9.1 | direct development | Starlette 1.3.1's supported test client |
| httpcore2 | absent | 2.9.1 | transitive development | Required by httpx2 |
| truststore | absent | 0.10.4 | transitive development | Required by httpx2's resolved graph |

No other package version changed. Starlette remains transitive rather than
becoming an application dependency. All four dependency artifacts —
`pyproject.toml`, `uv.lock`, `requirements.lock`, and `requirements-dev.lock` —
were regenerated together with hashes preserved.

The authoritative audit command is:

```bash
uv run --project backend pip-audit --strict --desc --require-hashes \
    --disable-pip --requirement backend/requirements.lock
```

It audits the exact deployable export as already-resolved input, propagates a
non-zero result, and does not ask the advisory service to identify the local
editable `dhruva` distribution. Disabling pip's second resolution step is
material: otherwise pip-audit's temporary environment omits `packaging`, which
is already present as environment tooling, from its reported dependency set.
Tests prohibit that omission, vulnerability ignores, exit-code suppression,
unhashed input and substitution of the developer environment for the deployment
lock.

The committed `v0.6.0.sbom.cdx.json` is CycloneDX 1.4 JSON generated from the
same hash-pinned deployment lock. Its 59 normalized package/version pairs equal
the audit set, and it contains no machine-local path.

An informational audit of the development export reports the pre-existing
`pytest==8.4.2` advisory `PYSEC-2026-1845`, fixed in pytest 9.0.3. Pytest is not
part of the deployment lock, the version did not change in this remediation, and
upgrading the test toolchain is outside this narrow runtime-security milestone.

## Framework compatibility surface

DHRUVA uses one FastAPI application factory, HTTP middleware, JSON/plain-text
responses, disabled documentation/OpenAPI endpoints, health/readiness/metrics
routes, and FastAPI's test client. Focused tests passed without application-source
changes. DHRUVA does not currently use form parsing, `StaticFiles`,
`HTTPEndpoint`, CORS, application WebSockets, streaming responses, or application
lifespan/startup/shutdown hooks. No speculative compatibility code was added.

## Migration and rollback

Upgrade the schema with the repository's migration command:

```bash
cd backend
uv run alembic upgrade 0012_rls_scaffolding
```

Migration `0012` can be downgraded to `0011_authorisation` if only the permissive
RLS scaffolding must be removed. A whole-S06 downgrade to `0006_idempotency`
drops credential, audit, session, principal, role and assignment data and is
therefore destructive. Do not downgrade the database merely to roll back an
application binary; deploy the preceding compatible binary and follow an
operator-approved data plan if schema rollback is genuinely required.

## Known limitations

- RLS remains deliberately permissive until S44; the restrictive form is tested
  as a non-owner role but is not the v1 deployment policy.
- Principal administration, role assignment and first-principal bootstrap have
  no operator command yet (TD-S06-9).
- Authentication and authorisation are application services, not exposed HTTP
  routes; authenticated route work requires a separate approved slice.
- The master key comes from the environment and automated key rotation is
  deferred to S42.
- Service principals and TOTP recovery are not modelled.
- ADR-060's Linux benchmark gate still needs its canonical Linux environment;
  Windows benchmark misses remain transparent and non-gating.
